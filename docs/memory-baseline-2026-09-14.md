# 后台内存基线与轻量化方向

日期：2026-09-14。对象：已发布的 v0.3.0 Windows amd64 二进制。此报告先回答内存现状；MSI 和应用内更新尚未实现，本次没有更改产品源码或发布新版本。

## 测量口径

- Windows 11 家庭版 10.0.26200，Intel Core i7-14700KF，28 个逻辑处理器，约 31.7 GiB 可见内存。
- 二进制 SHA-256：bff3ef2ae0cd0e87b49997bfd817c0d0b6cb7c40c4bbed483d041f27f5043167，与 v0.3.0 发布校验和相符。
- 主测量使用 Windows Get-Process，约每 200 ms 采样一次，记录 WorkingSet64、PrivateMemorySize64 和 TotalProcessorTime。主表是各场景内的中位数与采样峰值，不是理论最大值。
- 工作集表示当前驻留物理内存，包含共享页；私有提交表示进程私有的已提交虚拟内存，不等于当前物理内存，也不能和工作集相加。[Microsoft 指标说明](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)
- MiB = 1,048,576 字节。CPU 时间是所有线程累计的处理器秒数，不是墙钟时间或整机 CPU 百分比。短期空闲测得零增量不代表永久不耗 CPU。
- 数据、配置、设备身份均为缓存目录中的合成测试数据；不接触用户同步文件夹。只有 mDNS 空闲场景启用局域网发现，所有文件同步及随传均使用回环地址。
- A 端启用托盘，B 端关闭托盘；主表分别列两端，不能把两端之和当作单机应用占用。
- 1,000/10,000 个小文件均为 4 KiB、相同内容、两端预先存在。此场景测扫描/清单/规划，不代表不同内容首次复制、复杂目录树或大量冲突。
- 256 MiB 文件是单个合成文件，分别经文件夹同步和 HTTP 流式上传后 TLS 随传。控制器核对目标文件大小，程序执行内容摘要校验。
- 空闲、同步和浏览器数据来自短期样本；没有 24 小时稳定性、多文件夹高并发、真实蓝牙或其他平台实测，也没有同机竞品基准，不能据此宣称比竞品更省内存。

结论：主场景空闲工作集约 13–19 MiB，私有提交约 46–49 MiB；一般单任务约 50 多 MiB 私有提交。10,000 文件扫描采样峰值达到约 72 MiB，10,000 条历史记录轮询峰值约 80 MiB。全部数字均为本次单机合成数据样本，不是产品上限。

10,000 文件任务结束后静置 130 秒，A 端最后工作集/私有提交为 29.7/59.4 MiB，B 端为 22.9/56.4 MiB，均出现回落但没有回到首次启动水平。不能仅凭这一现象认定泄漏，也不能说任务结束后立刻全部归还。

另一次独立空闲启动采样，15 秒工作集保持约 48.4 MiB，私有提交约 46.0 MiB。因此工作集在不同启动及系统状态下有明显差异，不能只选低值宣传“固定低于 20 MB”。该次原始数据保存在 `.cache/memory-audit/idle-*/samples.json`。

历史压力数据是 10,000 条合成已完成发送记录、每条一个标记缺失的文件。轮询阶段用 HTTP 请求模拟页面每约 2.5 秒查询两个状态接口，不渲染 10,000 个 DOM 卡片；这测量的是后台响应成本，不是大历史页面的浏览器总峰值。

1,000 文件自动检查窗口 75 秒内，两端 CPU 分别约 0.56 和 0.70 秒；10,000 文件无变化检查连续两次，墙钟约 7.54 秒，两端分别约 5.20 和 5.95 CPU 秒。后者说明文件数增长时，无变化扫描仍然有可见处理器成本。

## 原始数据和复现

主场景脚本：`.cache/memory-audit/run.cjs`；采样器：`.cache/memory-audit/sample.ps1`；浏览器场景：`.cache/memory-audit/browser.cjs`。

在项目根目录执行：

```powershell
node .cache/memory-audit/run.cjs
$env:NODE_PATH = "$PWD/.cache/ui-tools/node_modules"
node .cache/memory-audit/browser.cjs
```

这些诊断脚本和原始采样均在忽略目录中，没有加入源码发布。主结果：`.cache/memory-audit/run-node-5PXO7v/results.json`；逐条采样：同目录 `samples.jsonl`；浏览器结果：`.cache/memory-audit/browser-zWhdLU/`。脚本会创建隔离实例并在结束时终止自己创建的进程。

尝试编译 Go 采样器时，系统拒绝启动 `D:/Program Files/Go/bin/go.exe`，项目本地 `.cache/toolchain/go/bin/go.exe` 也被拒绝，错误为“应用程序控制策略已阻止此文件”。本次转用可运行的发布程序和 Node/PowerShell 测量，没有修改系统策略，也没有声称执行了 Go 编译或测试。

## 后台组成及增长来源

| 部分 | 当前实现 | 内存及资源含义 |
| --- | --- | --- |
| 服务基础 | 一个 Go 进程承载 TLS 同步、HTTP 控制台、调度、发现和托盘 | 没有独立常驻浏览器内核或独立托盘进程；具体模块占用不能从进程计数器精确拆分 |
| 同步调度 | 每 2 秒唤醒，复制配置及状态，判断任务是否到期 | 不等于每 2 秒扫描文件。按文件夹间隔运行，另有 0–3 秒抖动和调度粒度 |
| 无变化扫描 | 到期后仍逐个读取普通文件计算 SHA-256；一次成功会话前后均扫描 | CPU/磁盘读取随文件数量与总大小增长。每个 hashFile 调用创建 256 KiB 缓冲，不能把所有缓冲相加当作同时存活内存 |
| 协议 | 每连接读写各 256 KiB 缓冲；控制帧完整 JSON 编解码 | 约 512 KiB 基础帧缓冲之外还有 TLS、JSON、清单和 Go 运行时。单帧上限 128 MiB，峰值不能保证固定几十 MiB |
| 同步清单 | 数组、路径和摘要、共同基线及规划 map 在会话中处理 | 文件数量越多，内存越大；不同同步空间可并发，未见全局扫描并发上限 |
| 随传 | 文件内容在磁盘暂存，流式收发；最多 4 个活动任务 | 文件体积不要求等量 RAM。重发会增加磁盘复制和读取，缓存文件不能算作全部常驻内存 |
| 随传历史 | 启动加载所有记录到 map；查询克隆、排序记录并核对文件存在性 | 无分页/常驻数量上限，历史累积会提高长期内存及网页轮询成本 |
| 活动日志 | 仅保留最近 200 条 | 此列表有明确数量边界 |
| 内容对象/文件历史 | 存在磁盘，对象按摘要去重 | 一般不全量常驻 RAM，但对象缓存和归档有磁盘成本 |
| 冲突操作 | 选择本地/远端版本时 os.ReadFile 读取整个对象；文本预览每对象限制 5 MiB | 大文件冲突解决可能按文件大小分配内存，是流式收发之外的重要例外；本次未做冲突峰值实测 |
| mDNS | 后台发现事件与库的退避查询；附近设备 map 保存已发现条目 | 没有发现时也会有查询；Nearby 用时间判断在线，当前 map 未见过期条目移除 |
| 配对请求 | 一分钟有效；部分过期清理由查询触发，成功请求删除 | 过期并不自动等于内存立即删除，长期会话状态有进一步设限空间 |
| Windows 托盘 | 原生隐藏窗口、图标和消息循环；菜单按操作生成 | 属于同一个进程，不是一个轮询刷新 UI 的额外浏览器 |
| 网页轮询 | app.js 和 transfer.js 各每 2.5 秒请求状态，标签页关闭后停止 | 即使只看同步页，随传脚本也会刷新。隐藏标签页没有应用自己的暂停策略；浏览器可能自行节流 |

## 浏览器与常驻服务应分别评价

独立无头 Chrome 打开一个空状态控制台，后台私有提交中位数从 47.6 MiB 增至 49.3 MiB，关闭专用浏览器后约 49.7 MiB。页面 JavaScript 已用堆约 1.38 MiB；这不包含 DOM、渲染、GPU 和浏览器本身。

本次专用 Chrome 进程快照中，各进程私有提交中位数之和约 322 MiB。这是整套测试浏览器的开销，不是 PolySync 页面在用户已有 Edge/Chrome 中的增量，也不能作为所有设备上的承诺值。工作集含共享页，因此不把浏览器各进程工作集简单相加当作独占 RAM。

轻量常驻应以“关闭控制台网页后，单个后台进程”作为主要验收条件，同时单独控制网页开销。

## MSI 与应用内更新的实施约束

以下为后续实现方向，尚未实现或验收。

1. Windows 提供 MSI，管理程序安装位置、开始菜单、卸载与同一产品系列的升级；用户数据与程序目录分离，升级保留配对、同步配置及历史。保留便携 EXE 作为可选分发形式。
2. 优先复用当前 Go 进程提供“检查更新”和“下载并安装”入口，不增加常驻更新服务或内嵌浏览器。
3. 更新包流式写入磁盘，不把 MSI 整包读入 RAM。检查失败显示可重试结果；校验版本与下载完整性，再进入安装流程。发布真实性校验需要明确的签名/信任设计，不能把同一下载源的 SHA-256 说成独立签名。
4. 安装前检查正在执行的同步/传输；有任务时提示稍后安装。空闲后优雅停止服务、释放端口，再由短时辅助进程/Windows Installer 完成升级与重启。失败必须有结果反馈和可恢复路径。
5. 自动检查如加入，应低频并带超时/退避；不为检查版本建立秒级轮询。蓝牙等可选协议也应按需启用，单独测量扫描及连接开销。

## 优化优先级

- 先修复大文件冲突恢复的整文件读取，改成受校验的流式写入，避免某条操作路径突然按文件大小占 RAM。
- 随传历史持久化查询/分页、限制常驻热记录，并为设备发现与过期会话增加清理边界。
- 减少无变化时的全目录读取，引入有边界的摘要缓存/文件索引，保留校验兜底；在监听器与轮询之间比较 CPU、唤醒与内存成本。
- 控制并发扫描、分块处理大型清单，复用合理大小的缓冲。
- 网页不可见时降低/停止非必要轮询，避免反复返回完整历史。
- 最后再评估 Go GC 参数；不能为了任务管理器瞬时数字反复强制 GC 或强制清空工作集。Go 的 GOMEMLIMIT 是软限制，不是整个进程的硬上限。[Go GC 指南](https://go.dev/doc/gc-guide)

建议先把“典型双设备、一个同步文件夹、有限历史记录、网页关闭时私有提交约 50 MiB 级，常规单任务尽量低于 100 MiB”作为待验证的工程目标，而不是现在对外承诺的上限。应补 24 小时运行及数周历史积累测试，并同时记录 CPU 时间、磁盘读取量、唤醒频率和任务结束后的回落。
